# 业务赋能规划师 (Business Enablement Planner)

S9 不再承担“让客户勾选固定赋能菜单”的角色，也不再输出预设模块化建议。S9 的唯一职责是作为策略层收口节点，**总结 S1-S8 已经发现的企业明显问题，并把这些问题转译为可执行的 GEO 业务建议**。

**上游**：S1-S8 全部产出 + 可选客户现状自检表  
**下游**：`S9_{brand}_业务赋能建议包.md` + `S9_{brand}_策略完整性检查.md` → S0 编排师

---

## 标准输出文件

| 输出物 | 文件名规范 | 格式 | 下游消费者 |
| :--- | :--- | :--- | :--- |
| 业务赋能建议包 | `S9_{brand}_业务赋能建议包.md` | MD | 客户、S0、后续内容生产层 |
| 业务赋能建议包（PDF） | `S9_{brand}_业务赋能建议包.pdf` | PDF | 客户；仅在 S0 统一询问并获得确认后生成 |
| 策略完整性检查 | `S9_{brand}_策略完整性检查.md` | MD | S0 编排师 |

> **源文件输出原则**：S9 节点只生成 Markdown 源文件。PDF 不在 S9 内生成；S1-S9 单节点 PDF 默认为跳过，仅在运行方显式启用时由 S0 在 S10 全景报告完成后统一生成，不询问、不等待、不暂停。

## 核心工作流

### Stage A：策略完整性检查

在生成业务建议前，必须先检查 S1-S8 的产出是否完整、逻辑是否自洽，并输出 `S9_{brand}_策略完整性检查.md`。完整性检查不是为了补齐旧版模块菜单，而是为了确认 S9 的问题总结是否有足够证据支撑。

完整性检查必须包含以下内容。

| 检查维度 | 检查重点 | 输出要求 |
| :--- | :--- | :--- |
| 资产清单核对 | S1-S8 必要 JSON/MD 是否存在，是否可解析 | 标记“已具备、部分具备、缺失” |
| 核心逻辑链条 | S1 事实、S2 意图、S4 定位、S5 诊断、S6/S7/S8 内容资产是否互相支撑 | 标记链条断点 |
| 证据可追溯性 | 每个问题是否能回溯到具体节点或文件 | 输出证据来源 |
| 样本限制说明 | 若 S5 为用户已接受的部分 AI 监测样本，必须先验证 `partial_accepted=true`，再说明成功/失败范围与分析口径 | 标注样本边界与置信度 |
| 遗留风险 | 仍需客户补充确认的信息 | 输出非阻断风险清单 |

### Stage B：S1-S8 企业问题综合诊断

S9 必须从 S1-S8 中抽取和归纳企业当前最明显的问题。问题必须是跨节点推导结果，不能凭空创造，也不能只复述某一个节点的结论。

问题总结至少覆盖以下八类来源。

| 来源节点 | 必须关注的问题类型 | 示例判断 |
| :--- | :--- | :--- |
| S1 品牌资产知识库 | 企业事实缺失、案例证据薄弱、资质背书不足、合规边界不清 | “品牌具备能力主张，但缺少可被 AI 引用的结构化事实证据。” |
| S2 营销图谱 | 用户意图覆盖不足、真实问题与品牌表达错位、负面疑虑未被回应 | “用户高频比较问题未被品牌现有内容承接。” |
| S3 品类趋势 | 趋势机会未被品牌叙事占位、品类词/场景词缺口 | “行业正在转向某类需求，但品牌内容仍停留在旧场景。” |
| S4 品牌定位 | 定位表达不清、差异化不足、可信理由不足 | “定位有主张但缺少 RTB 与可验证证据链。” |
| S5 品牌诊断 | AI 提及率低、排名靠后、情绪偏弱、竞品占位、信源缺口 | “AI 回答更常引用竞品或第三方站点，品牌自有资产没有成为默认信源。” |
| S5.5 语义资产审计 | 语义一致性不足、实体识别弱、关键事实不可机器读取 | “品牌语义资产尚未形成稳定的 AI 识别锚点。” |
| S6 品牌话语体系 | 话语 Token 与用户问题不匹配、卖点表达泛化、禁用语风险 | “品牌语言可读，但未形成可复用的 AI 友好答案模块。” |
| S7/S8 视觉与问答架构 | 视觉符号弱、问答树缺口、内容路径不完整、落地页结构不足 | “问题—答案—证据—转化路径之间未形成闭环。” |

S9 必须输出“问题优先级矩阵”，每个问题至少包含问题描述、证据来源、影响、严重程度、置信度与建议方向。若 S5 使用的是用户已确认接受的部分样本，必须在对应问题中说明成功/失败范围与样本限制，但不能将“样本少”本身当作业务问题。

### Stage C：GEO 业务建议生成

S9 的建议必须围绕 **GEO 业务增长** 展开，即让企业更容易被生成式 AI 识别、理解、引用、推荐与转化。建议不再按旧版固定模块分拆，而是按“问题—GEO 影响—建议动作—优先级”的方式组织。

必须覆盖以下建议域，但不要求把它们命名为旧赋能模块。

| 建议域 | 业务含义 | 建议输出 |
| :--- | :--- | :--- |
| 实体与事实资产修复 | 让 AI 能准确识别企业是谁、做什么、凭什么可信 | 企业实体信息补齐、产品/服务事实表、案例证据链、可引用证明材料 |
| AI 可见性与信源占位 | 提升 AI 回答中的被提及率、排名位次、正向情绪和引用概率 | 自有页面、第三方信源、行业目录、评测/案例页面的补强建议 |
| 问答内容资产建设 | 用 S2/S8 的真实问题补齐 AI 可引用答案 | 高优先级 FAQ、比较页、场景页、问题型文章与标准答案 |
| 定位与话语一致性 | 让 S4 定位、S6 话语和 S8 答案形成统一表达 | 核心主张、差异点、RTB、禁用表达、答案模板修正 |
| 网站与结构化数据 | 让官网和落地页更适合搜索引擎与生成式引擎读取 | 页面结构、Schema、实体页、FAQPage、Organization/Product/Service 标记建议 |
| 分发与引用路径 | 让内容进入 AI 更可能引用的渠道与页面类型 | 基于 S5 `citation_sources` 的渠道/信源建议；若无信源则说明需先建立基础信源 |

### Stage D：优先级行动路线图

S9 必须把建议整理成一个“优先行动清单”，用于 S10 全景报告数据与最终报告。该清单字段统一命名为 `recommended_business_actions`，不得退回旧版勾选菜单逻辑。每个行动项必须包含以下字段。

| 字段 | 说明 |
| :--- | :--- |
| `action_id` | 使用 `GEO_A1_entity_facts`、`GEO_A2_ai_visibility`、`GEO_A3_qa_assets`、`GEO_A4_positioning_language`、`GEO_A5_site_schema`、`GEO_A6_distribution_citations` 中的一个 |
| `title` | 行动标题 |
| `problem_linked` | 对应的企业问题编号 |
| `priority` | `P0`、`P1`、`P2` |
| `reason` | 推荐原因，必须引用 S1-S8 证据 |
| `expected_business_effect` | 预期业务效果，如提升 AI 可见性、缩短信任建立路径、修复竞品占位等 |
| `owner_hint` | 建议执行负责人或团队类型 |

若客户没有官网、官网极度陈旧，或 S8 落地页蓝图显示官网无法承接核心问题路径，S9 应将其写入 `GEO_A5_site_schema` 行动建议，供 S9 信源建设建议或外部官网改造团队承接。

## 产出交付规则

**产出交付规则（本工作流 覆盖）**：本节点不是全局暂停点时，必须把所有 JSON/MD/资产文件真实落盘并通过校验，但不得在对话框发送附件或展开正文；完成后静默交回 S0 继续。只有 S4.8 固定问题确认、S5.0 监控数据确认和最终交付允许面向用户发送文件。

**非暂停点声明（本工作流）**：本节点完成后只回传 S0 继续执行，不等待用户确认，不向对话框发送阶段附件。

## 校验闸门

| 校验项 | 标准 | 不通过动作 |
| :--- | :--- | :--- |
| 旧模块删除 | 正文不得回退为固定赋能菜单或预设板块，不得输出与 S1-S8 问题无关的泛化运营建议 | 打回重写 |
| 问题总结 | 必须总结 S1-S8 中发现的企业明显问题，且每个问题有证据来源 | 打回补充 |
| GEO 建议 | 必须围绕 GEO 业务建议输出，不得泛泛给运营建议 | 打回修改 |
| 优先级行动 | 必须输出 `recommended_business_actions` 行动清单，且每项包含 action_id、priority、reason、expected_business_effect | 打回补充 |
| 官网/Schema 建议 | 若发现官网承接问题，必须写入 `GEO_A5_site_schema` 行动建议，并说明原因与下一步 | 打回补充 |
| S5 部分样本 | 未有 `data_confirmation_status=confirmed` + `partial_accepted=true` 时必须阻断；已接受时写入样本边界、失败范围与置信度 | 打回修改 |
| 源报告 | `S9_{brand}_业务赋能建议包.md` 与 `S9_{brand}_策略完整性检查.md` 必须存在且非空；PDF 不作为 S9 完成条件 | 强制打回重做 |

## 本工作流 源文件质量底线

- 本节点必须生成详细、具体、可供 S10 读取的结构化 JSON 与 Markdown 源文件。
- 禁止只写标题、空表、空数组、空对象、模板占位、品牌名重复或“资料仍需补充/待补齐/暂无/TODO”。
- 若关键事实不足，必须基于已采集资料给出可追溯的阶段性判断，并在文件中列出缺口与下一步补证动作，不能产出空文件。
- 非暂停节点只落盘不对话框输出；由 S0 在最终交付中统一打包。

## 本工作流 来源深度与 S10 覆盖契约（强制）

本节点的所有输出必须遵循 `../shared/source-depth-and-coverage-contract.md`。除本节点既有 schema/方法要求外，还必须满足该契约规定的有效正文、结构层级、JSON 丰富度、占位/重复比例和文件命名要求。

产物不仅要“存在”，还必须能够被 S10 的 `source_manifest` 登记并通过 `source_coverage_gate`。禁止仅输出摘要、标题壳、空数组或与其他阶段高度雷同的通用文字；未达到门槛时应在本阶段补写，而不是把缺口留给 S10。

## 本工作流 Agent 执行硬规则：本阶段必须 Wide Research

当本 Workflow 在 外部 Agent 中运行时，`S9` 不得只用模型常识或聊天总结完成，必须独立调用 Wide Research，并将本阶段资料检索、证据来源、分析结论和规定产物落盘。

完成 `S9` 后必须写入：

```text
outputs/{brand_id}/_execution/S9_{brand_id}_wide_research_manifest.json
```

manifest 必须包含：

```json
{
  "stage_id": "S9",
  "used_wide_research": true,
  "status": "done",
  "research_queries": ["..."],
  "external_sources": [{"title": "...", "url": "...", "used_for": "..."}],
  "generated_files": ["..."],
  "evidence_notes": "..."
}
```

若本阶段没有 Wide Research manifest，S10 前的 `stage_execution_checker.py --strict` 必须阻断。不得用“并行研究完成”替代本阶段文件。
